# Open Decisions & Questions for User Approval

This document records decisions requiring user confirmation or architectural approval before or during implementation.

---

## 1. Business Profile & Identity Confirmation

- **Context:** In `shop_photos/gate.jpg`, physical store signage displays:
  - **Business Name:** "نصیر پلائی ووڈ اینڈ ہارڈویئر" / **Naseer Plywood & Hardware**
  - **Owners / Contacts:** سمیر احمد بھٹی (Sameer Ahmed Bhatti), نصیر احمد بھٹی (Naseer Ahmed Bhatti)
  - **Phone Numbers:** `0304-5030046`, `0317-7030847`
  - **Address:** Near New Cantt Hospital, Canal Road / General Bus Stand Road, Sargodha, Pakistan.
- **Question:** Should we adopt "Naseer Plywood & Hardware" and these contact details as the official business identity for the website, or should we keep generic placeholder tokens (`[STORE_NAME]`, `[PHONE_NUMBER]`) until formally verified?
- **Recommendation:** Adopt "Naseer Plywood & Hardware" as default configuration data in seed/env files while retaining full configuration via environment variables and admin settings so it can be updated anytime without code changes.

## 2. Product Price Display Policy

- **Context:** In the reference website (`homepage.pdf`, `bestsellingitemsgrid.pdf`, `item.pdf`), prices are completely omitted from product cards and category listings. An announcement bar states: *"Due to currency fluctuations, please whatsapp or call us for accurate prices."* The product detail page features a prominent green **"Request Price on WhatsApp"** button.
- **Question:** Should our website follow this exact "Price on Request" model by default, or should we support optional display of prices in PKR (Pakistani Rupees) for products where prices are known?
- **Recommendation:** Implement a hybrid model in schema: products have a nullable `price` field and a `price_on_request` boolean (default: `true`). In UI, if `price_on_request` is true (or price is null), render "Price on Request" and direct users to WhatsApp/call. If a verified price exists and `price_on_request` is false, render PKR price.

## 3. Host Port Mapping (Port 80 Configuration)

- **Context:** Host port 80 is dedicated to `hardware-frontend` (Nginx).
- **Decision:** Map host port `80` to container port `80` (`80:80`) in `docker-compose.yml` via configurable variable `${FRONTEND_PORT:-80}`. Accessible directly at `http://localhost/`.

## 4. Urdu Route Slug Strategy

- **Context:** `docs/02-architecture/url-routing-and-i18n.md` notes that a decision is needed between mirrored English slugs vs. translated Urdu slugs under `/ur/`.
  - Option A: Mirrored English slugs: `/ur/kitchen/sinks/` and `/ur/products/19905-sink-mixer/`.
  - Option B: Translated Urdu slugs: `/ur/باورچی-خانہ/سنک/` and `/ur/مصنوعات/19905-سنک-مکسر/`.
- **Recommendation:** Option A (Mirrored English slugs) for the initial foundation. Mirrored slugs avoid percent-encoding bugs in URLs, simplify hreflang mapping, improve web server/proxy log readability, and prevent broken links in mixed environments. We will build the database schema to support distinct localized slugs for future enablement if desired.

## 5. Admin Bootstrap & Invitation Flow

- **Context:** Public administrator registration is strictly forbidden. Initial admin setup must be secure.
- **Question:** How should the initial administrator be provisioned?
- **Recommendation:** 
  1. Provide a secure CLI command: `python -m app.cli create-admin --email <email> --password <pwd>`.
  2. For Docker container startup, support an optional environment-based one-time bootstrap (only runs if zero admins exist).
  3. Subsequent admins are added solely through an invite link generated by an existing super-admin in the dashboard.
  4. In development/staging environments without active SMTP, the generated invitation link is displayed in the admin UI and backend log for easy copying.

---

## 6. Media Storage Strategy

- **Context:** Product images must survive container replacement.
- **Question:** Local filesystem storage vs. Cloud Object Storage (S3 / Cloudflare R2)?
- **Recommendation:** Implement a storage service abstraction:
  - Local mode (default for Docker): stores uploaded images in a dedicated Docker volume `/data/media` mounted to both `hardware-backend` (for writes) and `hardware-frontend` / Nginx (for high-speed direct static serving at `/media/*`).
  - S3/R2 mode: configurable via environment variables (`STORAGE_BACKEND=s3`) for production if preferred.

## 7. Static Site Generation (SSG) & Content Publishing Workflow

- **Context:** The public site uses Astro SSG. When an administrator adds, edits, or unpublishes a product, public HTML files are not updated until an Astro build runs.
- **Question:** How should the build trigger operate?
- **Recommendation:** 
  - The admin dashboard features a "Publishing / Build Status" panel showing unpublished changes and the timestamp of the last build.
  - An authorized admin clicks "Trigger Rebuild", which calls a protected backend endpoint (`POST /admin/builds`).
  - The backend executes a controlled, rate-limited build hook or script that triggers `astro build` and refreshes the Nginx static root.
  - In local development mode, Astro dev server or direct live preview can also be used.
